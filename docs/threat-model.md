# Threat model (v1.1)

This document is the security contract for `svault` v0.1.0 (release prepared, unpublished — no tag, no published artifact, no independent audit). It is deliberately explicit about what the system does **not** protect against. Normative invariants are enforced by the test suite, not by convention.

## Assets

Secret values · key material in daemon RAM (MEK, DEK, audit MAC key) · agent tokens · confidentiality of `vault.enc` · integrity of `audit.jsonl` · availability (lock is an acceptable DoS against oneself; it protects confidentiality, never the reverse).

## Adversaries

| ID | Adversary | Outcome |
|---|---|---|
| A1 | Malware or root running as the user's account | **Wins.** Can read memory (ptrace/`/proc`), files, keystrokes, tokens. We shrink the window — no plaintext on disk, zeroize on lock, no secrets in argv/broker-env/logs (authorized `run` children excepted by explicit grant), idle auto-lock — but we do not claim isolation from A1 |
| A2 | Semi-trusted AI agent with shell/filesystem access (primary threat) | Confined to grants ∩ leases ∩ lock state, evaluated per request. Absence of credentials is never treated as human: management operations require positive human proof (the vault passphrase, verified against the key slots per request). An agent cannot unlock, cannot manage, cannot widen permissions, cannot read audit, cannot reveal without an explicit human approval. Broker impersonation is bounded, not eliminated (I11): a blind squatter that holds the instance lock but does not know the broker identity private key cannot obtain credentials — the signed handshake fails closed before any credential byte. A same-UID process that can read the broker identity file (`<vault>.broker-id`, mode 0600 but owned by the same UID) CAN forge handshake proofs and is NOT stopped; pins hold public keys only, so reading a pin buys nothing, but the guarantee stays bounded by filesystem permissions the adversary shares with the owner |
| A3 | Another local user | Blocked: socket 0600 in a 0700 dir + `SO_PEERCRED` UID check + 0600 files |
| A4 | Network / remote | No surface: the broker has no TCP listeners; MCP is harness stdio |
| A5 | Supply chain | Minimal direct dependencies, `cargo-deny` + `cargo-audit` in the local validation gate, manual review policy for new dependencies |

## Security invariants (testable contract)

- **I1 — No broker-side disclosure.** Secret values never appear in argv, in the CLI process, in logs, in error messages, or in audit entries — with two intentional exceptions: the approved agent `reveal` claim and the direct human `reveal` (passphrase- or session-authenticated) returning `{value}` are the only paths that return a secret value. Trap-secret tests scan every output channel.
- **I2 — Human unlock.** Unlocking requires an interactive TTY passphrase. No agent token can unlock. Passphrases are never accepted via argv or environment.
- **I3 — Positive human authentication.** Absence of credentials is never treated as human identity. Management operations (vault create/unlock, enrollment, grants, project/folder config, secret set/delete, audit inspection, approvals pending/approve/deny) require positive human proof — the vault passphrase, verified against the key slots on every request, or a server-minted human-session credential derived from that proof; agent-token requests on them are rejected (`E_HUMAN_REQUIRED`); credential-less requests are unauthenticated (`E_AUTH`), never human.
- **I4 — Encrypted at rest.** All values are XChaCha20-Poly1305 ciphertext under a DEK wrapped by a MEK derived through Argon2id; any tampering with `vault.enc` fails closed with `E_VAULT_CORRUPT`.
- **I5 — Kernel-contained writes.** The authorized-folder fd is acquired via `openat2` from a `/` anchor (`O_PATH`, no resolve flags) resolving the folder's relative path with `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS` (ancestor swaps fail closed, mount points stay traversable — only RESOLVE_NO_XDEV would forbid them); `inject_file` lands only beneath that pinned fd under the same three flags, mode 0600. Traversal, symlinks (leaf or intermediate), and TOCTOU are kernel-enforced, not application-checked. The fd is a capability over the directory resolved at acquisition time; later pathname renames do not redirect it.
- **I6 — Per-request capability.** Effective capability = grants(t) ∩ lease(t) ∩ lock-state, re-evaluated on every request; the `reveal` claim additionally rechecks the grant at claim. Revocation, grant reduction, and lock take effect on the next request (I8).
- **I7 — Tamper-evident audit.** Hash-chained entries; while unlocked, entries carry HMAC-SHA256 under a key HKDF-derived from the MEK (RAM only). Any rewrite/splice/removal of an entry preceding a MACed entry is detected. Every operation, allowed or denied, is audited; audit entries never carry secret values or token material.
- **I8 — Immediate revocation.** Revoking an agent, lease, or approval invalidates it for all subsequent requests; narrowing a grant invalidates affected leases/approvals; explicit and idle vault locks invalidate leases/approvals and drain all live runs (process groups, descendants included) through the same lifecycle, and that lifecycle runs once per expiry rather than once per later request. The idle lock is autonomous: the daemon arms its own wall-clock timer when a session goes idle, so the timeout is enforced with no request, connection, or client activity needed to trigger the check. Ownership is exclusive in one direction too — a session the daemon owns does not lock itself from inside an operation, because that path could only drop key material without draining managed runs (the run registry lives in the daemon); the watchdog is the single lifecycle owner, and a request path that also notices an expired window remains as defense in depth, not as the mechanism. No client-side state extends access.
- **I9 — Capability hygiene.** No agent token or lease credential in argv (no such CLI flag); token delivery via token-fd / token-file / env in that priority, lease credentials via `--lease-file`/stdin. Tokens are never logged, never audited, never inherited by broker-spawned children. A lease is presented by its 256-bit credential, resolved by SHA-256 digest, of which only the digest and an 8-hex display prefix persist — the public `lease_id` handle authorizes nothing. The MCP adapter holds lease credentials in its own process and substitutes them on the wire, so a capability never appears in an LLM transcript or tool result. A tool call that tries to supply a `lease` credential itself is refused rather than forwarded, so the adapter is the only source of a presented credential.
- **I10 — Approval binding.** Approvals bind (agent, project, key, reveal operation), are single-use, expire (pending and post-approval claim windows), and are not transferable. First `reveal` returns `E_APPROVAL_PENDING` + `{approval_id, expires_in}`; the claim returns `{value}` exactly once.
- **I11 — Local broker identity.** Exactly one broker may serve a socket: it holds an exclusive `flock(2)` on `<socket>.lock` for its whole lifetime, and a second broker fails closed with `E_BUSY` instead of unlinking and replacing the live socket. That lock check (kernel: peer UID equals the daemon owner via `SO_PEERCRED`, peer pid equals the lock holder via `/proc/locks`) stays as cheap defense in depth, but it authenticates *lock ownership*, never *what the peer is* — while the legitimate daemon is down any same-UID process can take the free lock and bind the path. The authority is the Ed25519 broker identity: the daemon owns a persistent keypair (`<vault>.broker-id`, mode 0600, generated once at first start), proves possession per connection via a signed `broker.hello` challenge-response (fresh client nonce + server nonce + socket-path bytes under domain `svault/broker-hello/v1`, so replays across nonces and sockets fail), and the client checks the proof against a per-socket TOFU pin (public key only) BEFORE writing any credential — mismatch, missing pin without explicit human trust, or bad signature fails closed with `E_BROKER_UNTRUSTED`, zero credential bytes written. What this closes: any listener that does not hold the identity private key (blind/opportunistic squatter, different-user attacker, rogue on a copied path), and it makes substitution loud (pin mismatch) instead of silent. What it does NOT stop: a same-UID process that can read `<vault>.broker-id` can forge valid proofs — 0600 does not stop the file's own owner, and A2 shares that UID — nor an adversary that wins the very first human-confirmed contact. An adversary that already reads every 0600 file as this user (A1; A2 with filesystem access) is NOT stopped. `E_VAULT_TOO_LARGE` marks the size refusal of I12.
- **I13 — Single mutable owner per vault.** Exactly one owner may mutate `vault.enc` at a time: the owner holds an exclusive `flock(2)` on `<vault>.lock` for as long as it may write, and a second owner (another `Session`, or a second daemon on any socket) fails closed with `E_BUSY`. This is what makes I8's "no lost update" true across processes: without it two holders each keep a private in-memory document and whichever saves second silently discards the other's committed change. The lock is per-vault, not per-socket, because the danger is the file, not the transport. The kernel releases it on process death, so a crash never leaves the vault unopenable.
- **I12 — Store-what-you-can-load.** No mutation is persisted unless the resulting file would be accepted by the loader: the writer validates against the same `MAX_FILE_LEN`/`MAX_HEADER_LEN` constants the parser enforces and refuses before the commit point with `E_VAULT_TOO_LARGE`, leaving the previously stored vault byte-identical. Parser-enforced KDF bounds (`MAX_M_KIB` = 256 MiB, `MAX_T` = 10, `MAX_P` = 8) and `MAX_SLOTS` = 8 key slots are part of that same contract: a header demanding more is refused as `E_VAULT_CORRUPT` **before** any Argon2 derivation runs, so a hostile header cannot buy unbounded CPU/memory. Each passphrase-carrying request costs one derivation per slot, so the slot cap is itself a cost bound.

## Explicit boundaries — what svault does NOT do

1. **`run_with_secrets` does not keep secrets from the agent.** The broker does not transmit values to the agent process — the spawned child, however, is created and controlled by the agent and can read and exfiltrate its own environment (`printenv`, HTTP calls, files). Granting `run` permits use of and potential exfiltration of those secrets by the agent-controlled child. Revoking the grant or agent, or locking the vault, terminates continued daemon-managed execution but cannot erase or recall copies retained or exfiltrated before revocation. What the broker guarantees is the narrower I1 boundary: values do not transit the CLI, responses, transcripts of tool results, logs, or disk.
2. **A `run` cwd is directory selection only, not sandboxing or containment.** `cwd` must be absolute and is authorized through `open_authorized_cwd` against the project's authorized roots (kernel `openat2` `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS` from the pinned root fd, applied via `fchdir` — no pathname, no TOCTOU). The child keeps normal OS filesystem access, including `..` — the same non-sandbox status as an injected `.env`, which is readable by any same-UID process. Containing the agent is the job of the OS sandbox (container, user namespaces, the harness's isolation), not of the broker. `svault` is an access-control layer, not a sandbox.
3. **Agent tokens can leak into agent transcripts** (the LLM can read its own token file). Accepted residual risk: a leaked token grants exactly the holder's existing grants — no escalation — and revocation (I8) kills it.
4. **Run cleanup is bounded, not a sandbox kill.** Each child runs in a dedicated process group (`pgid == pid`) so signals and cleanup are scoped to that run. Launch-connection disconnect, timeout, `timeout_secs` expiry, matching grant revocation, agent revocation, or vault lock atomically drains the relevant registry entries and kills the groups with `SIGTERM`, 250 ms grace, then `SIGKILL`; launch handlers wait/reap direct children. Natural exit races the drain atomically, so one path owns termination and stale entries/double-kill are avoided. A hostile child can still exfiltrate before the kill, and cleanup races a forking child — the guarantee is bounded cleanup scope and cessation of the managed process group, not isolation or recall of previously copied secrets.
5. **Run input and quota limits are fail-closed, not negotiated.** Exactly three `SCM_RIGHTS` FDs (stdin/stdout/stderr), CLOEXEC-owned from extraction (`MSG_CMSG_CLOEXEC`, `OwnedFd` from the first byte, closed on any error) and transferred once into the child — the broker never reads or logs child stdio. Caps: executable ≤4096 bytes; `argv` 1..256 entries ≤128 KiB aggregate (`argv[0]` is the child's `argv[0]`, only `argv[1..]` are arguments); `keys` ≤256 (omitted = all project secrets); caller `env` ≤256 entries ≤128 KiB aggregate, resultant child environment ≤1 MiB; 1 MiB wire message; 4 live runs per agent / 16 daemon-wide (excess → `E_BUSY`). Child environment is deny-by-default: allowlisted passthrough (exact: `PATH`, `HOME`, `TERM`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TMPDIR`, `SHELL`, `USER`, `XDG_RUNTIME_DIR`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME`) plus selected secrets; caller entries colliding with a selected secret are rejected, forbidden (`SVAULT_TOKEN`, uppercase `SVAULT_*`, `*TOKEN*`, `*PASSPHRASE*`, `*INTERNAL*`, `LD_*`, `DYLD_*`) or non-allowlisted entries are silently dropped; NUL in any surviving key/value is rejected. Run audit is safe structured fields only (`started`/`exited`/`denied`/`revoked`: actor, project, key names, `run_id`, executable except on denial/revocation, argv count never argv, cwd, stable `E_*` reason, outcome token, numeric exit code) — structurally unable to carry argv, environment, or secret bytes. `run_signal {run_id, signal}` is owner-only with the current `run` grant rechecked, delivered via `killpg` to that run's group.
6. **Bounded audit growth, with the lifecycle exempt.** The log has two ceilings: an operational limit for ordinary operations (`AUDIT_SOFT_LIMIT`) and a higher hard cap (`MAX_AUDIT_LEN`, matching the vault's `MAX_FILE_LEN`). The bytes between them are reserved for lifecycle events — lock, auto-lock, capability revocation, run drain — so a full log can never prevent a security action: runs are still terminated, capabilities invalidated and key material zeroized.

   Two orderings make this safe rather than merely bounded. **Ordinary mutations are refused before anything changes:** the ceiling is checked against the *exact* entry (measuring the resulting size, not just the current file length) and the audit entry is appended *before* `vault.enc` is replaced. The checkpoint embedded in the vault names that entry, so committing first and appending after would let a predictable condition strand a vault that can never be unlocked again; appending first makes a failure leave the vault untouched, and an orphan entry beyond the checkpoint is harmless (it is how reads and denials are already recorded). **Lifecycle events are best-effort:** their audit failure is not propagated, so the lock path completes regardless.

   Two kinds of lifecycle event are distinguished. **Authority-reducing** ones (agent/grant/lease revocation, a narrowing grant) are *applied* even when their entry cannot be written: refusing them would leave a capability alive, which is worse than a missing audit line. The checkpoint then stays on the last entry that really exists — it never names an entry that was not written — so `check_checkpoint` still succeeds and the vault stays loadable; the cost is one unrecorded revocation, reported on stderr rather than passed off as success. **Authority-holding** ones (lock, auto-lock) only drop key material. The same rule was applied to unlock itself, which previously propagated an audit failure and could be blocked by a full log — and could have replaced `E_AUTH` with an audit error, an oracle.

   Consequence for readers: an audit entry beyond the checkpoint does not imply the mutation landed (the log is ahead of the vault on every read/denial, on a crash between append and save, and when a revocation went unrecorded). Conversely, a missing entry does not imply the change did not happen. The vault document is the authority on what is authorized; the log is the authority on what was recorded.

   Nothing is truncated, rewritten or reordered, so history stays byte-identical and keeps verifying. The cap also bounds per-append cost, which is otherwise linear in file size because `resync` re-parses the log on every append (measured: 0.055 ms at 320 B, 0.52 ms at 100 KiB). Making appends O(1) means recovering the chain head from the tail rather than a full parse — a change to a security-relevant routine, deliberately bundled with rotation post-MVP. Rotation and archival are the designed replacement (post-MVP) — until they exist, a vault at the ceiling needs an operator, which is the honest failure mode for an append-only trail. Also bounded: the temp file `save_atomic` writes carries CSPRNG entropy and is created `O_EXCL`, so it cannot be pre-created or replaced by a symlink.

7. **Audit MAC limits.** The HMAC protects history against any writer that does not hold `K_audit` (i.e., everyone without root or the unlocked daemon's memory). Authentication is explicit: entries with a valid MAC are authenticated; `mac: null` entries (written while locked, or forged at the tail) are **unauthenticated** — a later MAC anchors their position and bytes but never their provenance, and rendering marks them. Documented, spec'd limitations: (a) truncation or forgery of the unauthenticated tail beyond the vault's audit checkpoint is not detectable (no external anchor) — truncation that reaches checkpointed entries IS detected (the encrypted vault embeds the `{seq, hash}` checkpoint of its last mutation, and unlock fails closed when the log is behind it); (b) root or an attacker reading the unlocked daemon's memory can recompute MACs (this is A1 winning).
8. **Unlock cost and connection intake are bounded.** A passphrase request costs one Argon2id derivation per key slot (≤8 slots, ≤256 MiB, ≤10 passes — see I12), performed **outside** the session lock, so a costly unlock never blocks cheap credential-free operations such as `vault.status` and a slow derivation cannot wedge the daemon. A freshly accepted connection must produce its first request within 5 s or it is dropped, so a client that connects and stays silent cannot pin one of the 32 connection slots; an established connection gets a 30 s idle timeout, and `run_with_secrets` is exempt because it deliberately holds its connection for the child's lifetime. Residual risk: a client that keeps sending valid first requests still consumes CPU per derivation — the caps bound the per-request cost, not the aggregate rate.
9. **Memory hygiene is best-effort, but coredumps are actively disabled.** Key types zeroize on drop and lock. The daemon process itself clears its dumpability (`prctl(PR_SET_DUMPABLE, 0)`) and sets `RLIMIT_CORE` to zero before it can hold any key material, so a fatal signal cannot yield a readable core of live MEK/DEK/`K_audit`; if either call fails the daemon still serves but logs a warning. `mlock`, swap encryption and OS-level coredump policy remain deployment hardening, not guarantees — and nothing here defends a process the operator launched without these two calls.
10. **Storage failures and vault size are fail-closed, not silent.** A failing `write(2)` (ENOSPC, EFBIG, EDQUOT, EIO) surfaces as an error to the caller — it is never retried into a spin — the temporary file is removed, and the destination file is left byte-for-byte intact; the daemon remains responsive. A mutation whose result would exceed the loader's own caps (`MAX_FILE_LEN`, `MAX_HEADER_LEN`) is refused *before* the commit with `E_VAULT_TOO_LARGE`, so the previously stored vault is never replaced by one the loader would reject. Note the `MAX_SECRETS × MAX_VALUE_LEN` model limits (640 MiB of values) exceed `MAX_FILE_LEN` (16 MiB): the size cap is the binding constraint and is enforced at write time.
11. **No recovery service.** Losing the passphrase loses the vault. Backup slots (reserved slot type) are the designed recovery path, post-MVP.

## Assurance

- TDD from spec scenarios; test suite covers traversal/symlink/TOCTOU races, auth/authz denial matrix, trap-secret leak grep across all channels, vault bitflips, protocol abuse, approval/lease state machines, and token hygiene.
- `cargo-deny`/`cargo-audit` in the local validation gate.
- Status: **no independent security audit.** Treat accordingly: start with disposable credentials, keep independent backups, and read this document before storing real secrets.
